Diagram grammar

Semantic and skin-independent: shapes and line styles carry meaning; a restyle may recolour them but may never reinterpret them. Every diagram ships with its legend and a provenance title block.

§ 01

Vocabulary

ClassRenderingMeaning
.e-money + .a-moneySolid, heaviest, accent greenReal money moves, or a synchronous call
.e-manual + .a-manualDotted, amber, round capsA manual / human step — not guaranteed
.e-mirror + .a-mirrorDashed, slateLedger mirror or async event — information, never money
.e-blocked + .a-blockedDashed, redA path that is designed not to exist
.n-svcSharp rectangleA system you own
.n-storeRounded rectangle, rx="10"Database, queue, ledger
.n-extDashed rectangleA system you do not control
.n-humanPill, rx = half heightA person or manual role
.n-label / .n-subSans 11px 600 / mono 9.5px mutedNode name / node type or note

Arrowheads are small filled triangles drawn as paths, sharing the edge's semantic class family. The convention: for an edge arriving at point (x, y) travelling rightward, the head is <path class="a-money" d="M x y l-9 -5 v10 z"/>; rotate the deltas for other directions.1

Canvas conventions: viewBox width 720 for full-width diagrams; nodes 120×44 (stores may be shallower); 10–12px between a node and its label baseline; edges leave and enter node mid-lines. Add role="img" and a meaningful aria-label to every SVG.

The label budget: text must fit its node. The mono sub-label runs ≈5.8px per character at 9.5px, so a 120-wide node holds ≈20 characters; the sans name label runs ≈6.2px per character at 11px, ≈19 characters. Over budget? Shorten the label or widen the node — overflowing text is a defect, not a style choice. Long detail belongs in the prose or a table, not crammed into a box.

1. Keep heads at 8–9px. Oversized arrowheads are the fastest way to make a schematic read as clip-art.

§ 03

Zoom levels (C4)

Diagrams follow the C4 model's zoom discipline: Context (the estate and its neighbours) → Container (the services inside it) → Component (inside one service). One diagram, one level — mixing levels is the most common way diagrams turn into mud. All examples below describe a fictional payments platform.

§ 04

Extended diagrams (Mermaid)

The native grammar above is Tier 1: hand-authored SVG for architecture and funds-flow diagrams, where the money semantics are the point. Everything else — sequence, state, class, ER, gantt, pie, git graphs, mindmaps, and the rest of the Mermaid catalogue — is Tier 2: authored as Mermaid DSL and rendered with the DDS theme bridge.

TierUse forSource of truthRendering
1 · Native grammarArchitecture, funds flow, anything using money/mirror/blocked semanticsInline SVG with grammar classesStatic — no JavaScript
2 · MermaidSequence, state, class, ER, gantt, pie, journey, git, mindmap, timeline…Mermaid DSL in a <pre class="mermaid">Hosted pages: vendor/mermaid.min.js + dds-mermaid.js. Final/self-contained documents: pre-rendered static SVG via mermaid-cli + mermaid-config.json

The DSL stays in the document — it is the diffable, reviewable source, and if scripts ever fail to load the text still reads (progressive enhancement, never a blank box).2 The theme bridge follows the page theme, including live data-theme flips. Sequence arrows carry the grammar's spirit for free: solid ->> means synchronous, dashed -->> means asynchronous.

2. Pre-rendering: npx -y @mermaid-js/mermaid-cli -i d.mmd -o d.svg --configFile mermaid-config.json — single-theme (light) by nature; use it for emailed or sandboxed output.

§ 05

Coverage — plan the set before you draw

Under-diagramming is a defect. One simplified overview is never enough for an investigation or design document. Inventory the content against this table and plan the full set before writing:

The content contains…Then draw…Tier
An end-to-end flow told across sectionsA detailed overview map (Container level) as the centrepiece, plus a zoom-in per load-bearing section1
A step-by-step interaction (webhooks, API calls)A sequence diagram2
A lifecycle, status machine, or ordered pipelineA state diagram2
Entities and their relationsAn ER diagram2
Phases, schedules, deadlinesA gantt chart2
Proportions or breakdownsPie / bar via --dds-v1…v62
A hierarchy or decompositionMindmap / flowchart2
  • If prose narrates a flow, sequence, or lifecycle step by step, it must also be drawn — narration is not a substitute.
  • Number every drawing (DWG XX-01…) and reference it from the prose.
  • One diagram = one zoom level = one type. Crowded? Simplify by splitting, never by merging or dropping load-bearing information.
  • Pre-rendered Tier-2 figures pin the light ground (style="background:#FBFAF3") so baked light-theme SVG stays readable in dark mode — the one sanctioned literal hex.
§ 06

Rules

  • One diagram, one C4 level. Split rather than mix.
  • Title block on every diagram — no exceptions, including drafts (drafts say in-review). Legend wherever grammar classes are used.
  • Diagrams are vector: Tier-1 inline SVG or Tier-2 Mermaid-rendered SVG. Never ASCII art, never raster exports. Canvas is reserved for data visualisation past ~10,000 marks — never for diagrams.
  • Tier-2 sources ship in the page: the DSL is the reviewable artefact, the render is presentation.
  • All colour through the semantic classes or the theme bridge; no literal stroke="#…" on grammar elements, no per-diagram theme overrides.
  • Flow reads left→right (or top→bottom for mirrors); avoid crossing edges before adding a node.
  • Blocked edges (.e-blocked) exist to make an absence visible — use them when the absence is the finding.
