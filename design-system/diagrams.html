Diagram grammars

Native SVG first. Node kinds and routes each own a hue, motion shows direction, and every drawing ships with its legend and a provenance title block. A restyle may recolour the grammar; it may never reinterpret it.

Modifiers on a node group: is-hot (thicker stroke — on the hot path), is-fail (red stroke, crit fill), is-new (dashed outline; write the kind line as CACHE · PROPOSED). Furniture: .dds-zone / .dds-zone.trust + .dds-zlabel for VPCs, regions and trust boundaries; .dds-stage column labels; .dds-step numbered badges keyed to a .dds-steps list; .dds-elabel edge labels with a surface halo. Add .dds-flow to march an edge's dashes, and a .dds-pkt circle with <animateMotion> on the same path to send a packet along it.

§ 03

Sequence grammar

Actors are .dds-node groups with a kind class, so a sequence shares its colours with the container view it zooms into. Lifelines are .dds-life; activations are rect.dds-act with the actor's kind class; messages are path.dds-msg with a route class (sync, async, data, ext, fail) or ret for returns, labelled with .dds-mlabel. Notes are g.dds-note (rect + text). Space messages 35–45 units apart; put the label 8 units above its arrow.

§ 04

State-machine grammar

States are g.dds-node.dds-st pills (rx = half height) coloured by status semantics: neutral pending, info in flight, ok done, warn reversed or lapsed, crit failed. Transitions are .dds-edge paths with the route class that names their trigger — sync for API commands, async for webhooks and events, ctrl for timers, fail for failures. .dds-st-init marks the start; .dds-st-final + .dds-st-final-dot the end.

§ 05

Funds-flow grammar (v1)

Unchanged from v1 and still the right tool when the semantics are money: what moves real money, what is a human step, what is only a mirror, and what is designed never to happen.

Vocabulary

ClassRenderingMeaning
.e-money + .a-moneySolid, heaviest, accent greenReal money moves, or a synchronous call
.e-manual + .a-manualDotted, amber, round capsA manual / human step — not guaranteed
.e-mirror + .a-mirrorDashed, slateLedger mirror or async event — information, never money
.e-blocked + .a-blockedDashed, redA path that is designed not to exist
.n-svcSharp rectangleA system you own
.n-storeRounded rectangle, rx="10"Database, queue, ledger
.n-extDashed rectangleA system you do not control
.n-humanPill, rx = half heightA person or manual role
.n-label / .n-subSans 11px 600 / mono 9.5px mutedNode name / node type or note

Arrowheads are small filled triangles drawn as paths, sharing the edge's semantic class family. The convention: for an edge arriving at point (x, y) travelling rightward, the head is <path class="a-money" d="M x y l-9 -5 v10 z"/>; rotate the deltas for other directions.1

Canvas conventions: viewBox width 720 for full-width diagrams; nodes 120×44 (stores may be shallower); 10–12px between a node and its label baseline; edges leave and enter node mid-lines. Add role="img" and a meaningful aria-label to every SVG.

The label budget: text must fit its node. The mono sub-label runs ≈5.8px per character at 9.5px, so a 120-wide node holds ≈20 characters; the sans name label runs ≈6.2px per character at 11px, ≈19 characters. Over budget? Shorten the label or widen the node — overflowing text is a defect, not a style choice. Long detail belongs in the prose or a table, not crammed into a box.

1. Keep heads at 8–9px. Oversized arrowheads are the fastest way to make a schematic read as clip-art.

Zoom levels (C4)

Diagrams follow the C4 model's zoom discipline: Context (the estate and its neighbours) → Container (the services inside it) → Component (inside one service). One diagram, one level — mixing levels is the most common way diagrams turn into mud. All examples below describe a fictional payments platform.

§ 06

Mermaid fallback (Tier 2)

Native SVG is now the default for architecture, sequence and state diagrams. Mermaid remains Tier 2 for the shapes the native grammars do not cover — ER, class, gantt, pie, journey, git graphs, mindmaps, timelines — and as a quick draft for a sequence or state diagram that will later be redrawn natively. It is authored as DSL and rendered with the DDS theme bridge.

TierUse forSource of truthRendering
1 · Native architecture grammarArchitecture / container views, sequence, state machinesInline SVG with .dds-arch / .dds-seq / .dds-stateStatic SVG, CSS motion only
1 · Funds-flow grammarMoney movement: money / manual / mirror / blocked semanticsInline SVG with .e-* / .n-*Static — no JavaScript
2 · MermaidER, class, gantt, pie, journey, git, mindmap, timeline…Mermaid DSL in a <pre class="mermaid">Hosted pages: vendor/mermaid.min.js + dds-mermaid.js. Final/self-contained documents: pre-rendered static SVG via mermaid-cli + mermaid-config.json

The DSL stays in the document — it is the diffable, reviewable source, and if scripts ever fail to load the text still reads (progressive enhancement, never a blank box).2 The theme bridge follows the page theme, including live data-theme flips. Sequence arrows carry the grammar's spirit for free: solid ->> means synchronous, dashed -->> means asynchronous.

2. Pre-rendering: npx -y @mermaid-js/mermaid-cli -i d.mmd -o d.svg --configFile mermaid-config.json — single-theme (light) by nature; use it for emailed or sandboxed output.

§ 07

Coverage — plan the set before you draw

Under-diagramming is a defect. One simplified overview is never enough for an investigation or design document. Inventory the content against this table and plan the full set before writing:

The content contains…Then draw…Grammar
An end-to-end flow told across sectionsA detailed container view as the centrepiece, plus a zoom-in per load-bearing section.dds-arch
Money moving between partiesA funds-flow drawing (money / manual / mirror / blocked).dds-diagram
A step-by-step interaction (webhooks, API calls, retries)A sequence diagram.dds-seq
A lifecycle or status machineA state diagram.dds-state
An ordered pipeline (ETL, batch, CI)A left-to-right container view with stage labels.dds-arch
Entities and their relationsAn ER diagramMermaid
Phases, schedules, deadlinesA gantt chart, or .dds-timeline for one rolloutMermaid / component
Where the latency goesA .dds-budget barcomponent
Proportions or breakdownsPie / bar via --dds-v1…v6Mermaid
  • If prose narrates a flow, sequence, or lifecycle step by step, it must also be drawn — narration is not a substitute.
  • Number every drawing (DWG XX-01…) and reference it from the prose; key long flows with .dds-step badges and a .dds-steps list.
  • One diagram = one zoom level = one type. Crowded? Simplify by splitting, never by merging or dropping load-bearing information.
  • Pre-rendered Tier-2 figures pin the light ground (style="background:#FBFAF3") so baked light-theme SVG stays readable in dark mode — the one sanctioned literal hex.
§ 08

Rules

  • Colour is meaning: every node kind, route and state hue used in a drawing appears in its legend, and nothing is coloured for decoration.
  • Title block on every diagram — no exceptions, including drafts (drafts say in-review).
  • All colour through the grammar classes and tokens; no literal stroke="#…" or fill="#…" on grammar elements.
  • Motion is directional: .dds-flow only on edges whose direction matters, packets on at most three routes (the hot path). Both stop under prefers-reduced-motion.
  • Text must fit its node: at 12px the mono detail line runs ≈7.2px per character and the 15px name ≈8px — a 200-wide node holds ≈24 and ≈21 characters. Shorten or widen; never overflow.
  • Diagrams are vector: native SVG or Mermaid-rendered SVG. Never ASCII art, never raster exports.
  • One diagram, one C4 level. Flow reads left→right; avoid crossing edges before adding a node.
  • Every SVG has role="img" and an aria-label that narrates the flow, including where it fails.
